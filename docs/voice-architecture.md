# 语音对话现状架构（dsh-voice-dialog 0.8.1）

## 一条回答怎么出门

```
页面（浏览器）                                后台（host 插件）
-------------                                 -----------------
麦克风 -> 切段 -> 识别 -> 声纹
        |
        v
  说话队列 SpeechScheduler  <-- 这份状态只活在页面里
        |  规则 + 模型判官（/organize、/plan）决定：打断 / 排队 / 不回
        v
     交给模型  ---------------------------------->  模型流式回答
                                                    |
                                            llm/stream 钩子：切句 -> 改写
                                                    v
                                            出声队列 TtsQueue（后台）
                                             每句合成语音 -> 帧
                                                    v
   TtsPlayer：音量 -> 提升 -> 限幅 -> 扬声器  <--SSE--
```

## 两个队列，位置不同

1. **出声队列（TtsQueue）在后台。** 后台知道从这句之后还排着几句、正在合成哪一句。页面只是播放端。
2. **说话队列（SpeechScheduler）在页面。** 你的话和客人的话排在第几位、谁在打断谁、哪句还没交给模型，只有页面知道；后台只在做一次判断时收到一份摘要（新话、正在读、还没读、排几条、上一句）。

## 因此现在的断点

- 后台看不见说话队列：现场出问题只能翻日志猜。
- 刷新页面：页面里排着的话和正在进行的判断全丢，等于清空。
- 判官拿到的是摘要不是真队列：连续说话时，后面几句很容易被判成“重复上一句”丢掉。
- 页面与后台两份时序各自记账，谁先谁后只能靠时间戳对齐。

## 要改就改这一处

把**决定状态**搬到后台：

- 后台持有：待说的话、正在读的句子、谁在说话、每条话的去留。
- 页面只保留：麦克风采集、声纹打标、播放。
- `src/scheduler.ts` 从“页面内调度”变成后台主控，页面变成薄客户端，事件上行、指令下行。

这样连续说话有完整上下文，刷新不丢队，后台随时能看到队里有什么。

## 目标形状（按主人口述改）

四条线并行，互不等待：

1. **说话计划线**：主模型在自己的思维链里直接下指令（说什么、先说哪句、要不要压住、等我说完），后台读到就执行。不再由第二个小模型去猜意图，也不再抢 1.2 秒超时。
2. **回答线**：主回答照常流式输出，只负责切句和合成。
3. **干活线**：真正跑工具、读文件、构建的那一层独立出来，只向上报两件事——在做什么、到哪一步。说话线把它转成人话，不必等它跑完。
4. **播放线**：页面只收帧、只出声，不做判断。

共享一份状态：谁在说、说了什么、读到哪、还排着几句。状态在后台，刷新不丢。

语音关掉时这条链路整体透明，不进任何一条线。


## 分层（主人口述，取代“判别架构”）

不再由一个独立的判官决定要不要说话；改成四层加一条共享状态，一切都可感知，不用硬切换。

1. **收听清洗层**：麦克风切段、识别、声纹、去噪去重。它产出两样东西：一句话，和一次“说话开始 / 说话结束”。
2. **思考推理层**：模型本身。它看得见状态（谁在说、谁说完了、现在读到哪句），不需要别人替它判断。
3. **执行层**：工具、读文件、构建。和推理分开跑，只往上抛“在做什么、到哪一步”。
4. **语言组织层**：所有带标记的朗读请求都收到这里，包括思维链里冒出来的那些，由它决定先后、合成、出声。

关键：**感知，不是切换**。模型随时知道谁开始说、谁停下、停了多久、自己读到哪；这些是状态，不是一次性的开关判断。

判官（现在那套打分）降级成可选，不再卡在流水线上，也不再独占“该不该回”这个决定。
